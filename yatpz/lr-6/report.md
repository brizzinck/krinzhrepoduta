# 1. Вступ (Introduction)

## 1.1 Мета (Purpose)

Тест-план фіксує, що, як, коли і чим тестується вебзастосунок Toolshop у циклі з 2026-11-30 до 2027-01-20. Він дає команді й замовнику одну погоджену основу: обсяг, критерії, графік і відповідальність. На нього спираються план і прогони в TestRail та рішення про випуск. Структура відповідає основним розділам стандарту IEEE 829 (нині ISO/IEC/IEEE [29119-3]{style="white-space:nowrap"}).

## 1.2 Загальні відомості (Background)

Practice Software Testing, або Toolshop, — це демонстраційний інтернет-магазин ручних і електричних інструментів, який автори підтримують для навчання тестуванню (<https://practicesoftwaretesting.com>, версія v2.5, збірка від 2026-10-11). Інтерфейс написано на Angular 20, серверна частина — REST API на Laravel 12 (PHP 8.3), база даних MariaDB 10.6; API описано в Swagger UI на api.practicesoftwaretesting.com.

Основні функції:

- каталог із фільтрами за категорією, брендом і ціною, пошук, сортування; сторінка товару з кошиком, обраним і порівнянням;
- кошик і оформлення замовлення за чотири кроки (кошик, вхід, адреса, оплата), пʼять способів оплати, знижки;
- реєстрація, вхід, відновлення пароля, блокування акаунта, двофакторна автентифікація;
- акаунт: профіль, зміна пароля, обране, рахунки з PDF, повідомлення; контактна форма з вкладенням; оренда техніки;
- панель адміністратора: товари, категорії, бренди, замовлення, користувачі, повідомлення, звіти.

Особливості: публічний стенд очищає дані щогодини; є версії Sprint 1-5 і «Sprint 5 (with bugs)», у локальній копії версію задає змінна `SPRINT` у файлі `.env`; є стандартні акаунти адміністратора й покупців (облікові дані не наводяться). Основа тестування: User Stories v5 і критерії приймання з документації проєкту, специфікація API в Swagger.

## 1.3 Обсяг тестування (Scope)

| Тестується | Не тестується (і чому) |
|:---------------------------------------------|:---------------------------------------------|
| Каталог: категорії, бренди, фільтр за ціною, сортування, пагінація | Вхід через Google і GitHub: сторонній OAuth, команда його не контролює |
| Пошук: запит від 3 до 40 символів | Реальна оплата: на демонстраційному стенді немає справжнього платіжного шлюзу |
| Сторінка товару: кількість, кошик, обране, порівняння | Листи в справжню скриньку на публічному стенді: доступу до скриньки немає; листи перевіряються в MailCatcher на локальній копії |
| Кошик і оформлення замовлення: чотири кроки, способи оплати, знижки | Чат-віджет і навчальні сторінки Testing Guide та Bug Hunting: це не функції магазину |

# 2. Підхід до тестування (Test Approach)

## 2.1 Стратегія (Strategy)

Пріоритет задає ризик. Високий: автентифікація, кошик, оформлення замовлення, рахунки. Середній: каталог, пошук, профіль. Низький: контактна форма, мова. Метод чорної скриньки: класи еквівалентності, граничні значення, тест-кейси в TestRail, дослідницькі сесії з обмеженим часом. Кожну збірку перевіряють у такому порядку: Smoke, нова функціональність, регресія; регресія модулів високого пріоритету автоматизована (Playwright, Newman) і запускається на кожній збірці. Середовищ два: локальна копія в Docker (основне: керовані дані, перемикання версії, MailCatcher) і публічний стенд (лише Smoke і браузери). Ролі: QA-інженер готує й виконує тести та веде дефекти; розробники виконують модульне тестування й виправлення; замовник проводить приймання й затверджує випуск.

Життєвий цикл дефекту в Jira: New, Assigned, Fixed, Retest, Closed або Reopened; кожен дефект повʼязаний із тест-кейсом у TestRail. Тестування призупиняється, якщо Smoke не пройдено або середовище недоступне понад 4 години, і відновлюється після успішного Smoke нової збірки. Відомі дефекти й відхилення попереднього циклу входять до першого регресійного набору: адреса з двома крапками в реєстрації (DEF-01), розкриття наявності акаунта у формі відновлення (DEF-04), немає помилки для пошуку коротшого за 3 символи (DEF-05), пошук приймає понад 40 символів (DEF-06), Sign out недоступний із клавіатури (DEF-12), блокування акаунта настало після двох невдалих входів замість трьох (спостереження з тестування попереднього циклу, TC-AUTH-06; дефект не оформлено, потрібна повторна перевірка).

Ризики циклу і заходи:

| Ризик | Як зменшуємо |
|:-----------------------------------------|:-----------------------------------------|
| Публічний стенд очищає дані щогодини | Скрипти створюють акаунти й дані на початку кожної сесії; довгі сценарії виконуються на локальній копії |
| Акаунт блокується після кількох невдалих входів (за вимогою після трьох, у попередньому циклі вже після двох), HTTP 423 | Окремі акаунти для негативних тестів входу |
| Публічний стенд спільний, тому викривлює показники продуктивності й заважає іншим користувачам | Навантажувальні тести лише на локальній копії |
| Немає доступу до справжньої скриньки | MailCatcher на локальній копії |

## 2.2 Етапи тестування (Testing Stages)

| Етап | Хто | Мета | Критерій входу | Критерій виходу |
|:-----------|:-------------|:----------------------------|:-------------------|:-----------------------------|
| Модульне | Розробники | Перевірити окремі класи й методи API на Laravel (Pest) | Код збирається | Усі модульні тести зелені, звіт про покриття додано |
| Інтеграційне | QA | Перевірити, що кінцеві точки REST API повертають правильні коди й дані та працюють із БД (Postman, Newman) | Модульний етап пройдено, API розгорнуто | Усі перевірки API пройдені, немає відкритих Critical і High |
| Системне | QA | Повні сценарії інтерфейсу, функціональні й нефункціональні види з 2.3 | Smoke пройдено, тест-кейси перевірено, середовище й дані готові | Виконано 100% запланованих кейсів, пройдено щонайменше 95%, немає відкритих Critical і High, для кожного Medium є рішення |
| Приймальне | Замовник і QA | Основні сценарії користувача: реєстрація, пошук, покупка, рахунок | Вихідні критерії системного етапу виконано | Замовник підписав приймання, Test Summary Report прийнято |

## 2.3 Види тестування (Testing Types)

| Вид | Що перевіряємо в Toolshop | Інструмент |
|:-------------|:--------------------------------------------|:---------------------|
| Smoke | Відкриття каталогу, вхід, додавання в кошик, початок оформлення | Playwright |
| Функціональне | Усі модулі з обсягу за тест-кейсами | Вручну, TestRail |
| Негативне й валідація | Поля форм: формат email, довжина пароля від 8 символів, пошук від 3 до 40 символів, вкладення контактної форми | Вручну |
| Регресійне | Модулі високого пріоритету після кожного виправлення | Playwright, Newman |
| API | Коди відповідей, схема JSON, токен автентифікації | Postman, Newman |
| Безпеки | Доступ до `/account` і `/admin` без входу, розкриття наявності акаунта у відновленні пароля (DEF-04), блокування акаунта, XSS у пошуку й контактній формі; пасивне сканування на локальній копії | OWASP ZAP, DevTools |
| Продуктивності | Каталог і пошук під навантаженням 25-50 віртуальних користувачів на локальній копії | JMeter 5.6.3 (HTML-дашборд) |
| Сумісності | Chrome, Firefox, Edge, WebKit, мобільне вікно шириною 390 px | Playwright (проєкти) |
| Зручності й доступності | Навігація з клавіатури, зокрема DEF-12 (Sign out) | Вручну |
| Локалізації | Перемикання мови, тексти не обрізаються | Вручну |

# Висновки

Я склав тест-план для Toolshop із шести розділів методички. План задає обсяг із девʼятьма виключеннями, чотири етапи з критеріями входу й виходу, десять видів тестування з інструментами, десять артефактів, перелік програмного забезпечення та інструментів і календар із шістьма контрольними точками. Я зʼясував, як ризики впливають на план: погодинне очищення стенда виносить довгі сценарії на локальну копію, а блокування акаунта після невдалих входів вимагає окремих акаунтів для негативних тестів. Критерії входу й виходу з 2.2 привʼязані до M4-M6, тому рішення про випуск спирається на вимірювані умови. План описує майбутній цикл, результатів виконання в ньому немає.
