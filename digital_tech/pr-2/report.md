# Практична робота 2

**Тема:** «Аналіз цифрових компетентностей професійних ролей у розробці програмного забезпечення»

**Мета роботи:** Навчитися співвідносити компетентності DigCompUA з реальними завданнями, інструментами та відповідальністю фахівців, залучених до розроблення програмного забезпечення.

## Завдання

Роботу виконано індивідуально; обрано роль Software Engineer.

1. Проаналізувати роль: завдання, інструменти, ресурси, проблемні ситуації, відповідальність.
2. Побудувати матрицю не менше ніж із восьми компетентностей DigCompUA.
3. Розглянути одну інженерну ситуацію: компетентності, наслідки, дії, інструменти.
4. Підготувати презентацію на 3–5 слайдів.

### Завдання 3. Інженерна ситуація: API-ключ у відкритому репозиторії

Ситуація. Розробник випадково закомітив у відкритий репозиторій GitHub файл конфігурації з ключем платіжного шлюзу (умовне значення `sk_live_EXAMPLE_NOT_A_REAL_KEY`). Сканери зловмисників знаходять такі ключі за лічені хвилини.

Потрібні компетентності (рядки таблиці 2): C4.K2 (рядок 6), щоб відкликати ключ і винести секрет зі сховища коду; C5.K1 (рядок 8), щоб оцінити масштаб за журналами; C3.K3 і C3.K1 (рядки 4–5), щоб повідомити команду й узгодити `git push --force`; C0.K3 (рядок 1) для `git filter-repo` і gitleaks у CI; C4.K1 (рядок 7) для 2FA на акаунті, з якого стався витік.

Наслідки недостатнього рівня. Несанкціоноване використання ключа (платежі від імені компанії, доступ до даних клієнтів); фінансові й юридичні втрати за порушення захисту персональних даних; втрата довіри клієнтів. Видалення файлу лише з останнього коміту лишає ключ в історії, а без відкликання він чинний; без автоматичних перевірок інцидент повториться.

Професійні дії та інструменти:

1. Відкликати ключ і випустити новий (кабінет провайдера).
2. Оцінити масштаб: журнали й транзакції від моменту публікації (журнали провайдера).
3. Винести ключ у змінну середовища або сховище секретів (GitHub Secrets, Vault, `.env` у `.gitignore`).
4. Видалити ключ з історії й оновити віддалений репозиторій (`git filter-repo`, BFG, `git push --force`).
5. Повідомити команду й відповідальних, за потреби клієнтів (Jira, месенджер).
6. Запобігти повторенню: gitleaks у pre-commit і CI, GitHub push protection; провести ретроспективу.

## Відповіді на контрольні запитання

**1. Що таке професійна роль у команді?** Це сукупність завдань, відповідальності, знань, умінь і компетентностей фахівця в команді програмного проєкту.

**2. Які ролі можуть бути в команді?** Software Engineer, QA Engineer, DevOps Engineer, Business Analyst, Data Engineer, Cybersecurity Engineer, UI/UX Designer, Project або Product Manager.

**3. Чому знання мов програмування недостатньо?** Робота інженера охоплює ще вимоги, проєктування, тестування, впровадження й супровід, де потрібні робота з інформацією, співпраця, безпека й розв’язання проблем. Ситуація з API-ключем це показує: мова програмування не допоможе відкликати ключ, оцінити масштаб витоку й домовитися з командою.

**4. Як компетентності пов’язані з професійними завданнями?** Завдання вимагає компетентності, компетентність реалізується цифровим інструментом, а інструмент дає результат. Наприклад, code review потребує співпраці (C3.K3), виконується в GitHub, а результатом є Pull Request із результатами review.

**5. Які компетентності потрібні Software Engineer, QA Engineer і DevOps Engineer?** Усім трьом потрібні робота з даними, співпраця, безпека й розв’язання технічних проблем. Software Engineer додатково потрібні програмування й вибір залежностей, QA Engineer планування тестування й аналіз дефектів, DevOps Engineer автоматизація збирання й розгортання та аналіз журналів і показників.

**6. Чому однакова компетентність застосовується по-різному?** Бо в кожної ролі свої завдання. Уміння аналізувати дані Software Engineer використовує для пошуку причин помилок, QA Engineer для оцінювання результатів тестування, а DevOps Engineer для аналізу журналів і показників системи.

**7. Що може підтвердити сформованість компетентності?** Окрім сертифікатів і тестів: програмний код, GitHub-репозиторій, Pull Request, результати code review, автотести, налаштований CI/CD-конвеєр, технічна документація, звіт про аналіз вразливостей.

**8. Які компетентності потрібні для командної розробки й code review?** Співпраця в цифровому середовищі (Git, GitHub, GitLab), критичне оцінювання чужого коду, комунікація для аргументованих зауважень і дотримання правил інформаційної безпеки.

**9. Які компетентності потрібні для безпечного використання бібліотек, API й зовнішніх сервісів?** Критичне оцінювання, щоб перевірити версію, ліцензію й вразливості бібліотеки (NVD, Dependabot). Захист даних, щоб тримати ключі API поза репозиторієм (Vault, GitHub Secrets), і захист облікових записів (2FA).

**10. Чому важливо критично оцінювати інформацію?** Документація може бути застарілою, а порада чи згенерований ШІ код помилковими. Невдалий вибір бібліотеки ризикує всім продуктом, тому джерела й залежності треба перевіряти.

**11. Чим базовий рівень відрізняється від достатнього й високого?** Базовий означає типові операції за інструкцією, достатній означає самостійне розв’язання стандартних завдань. Високий означає складні й нестандартні завдання, обґрунтований вибір технологій і допомогу команді.

**12. За якими критеріями визначити необхідний рівень для ролі?** За складністю завдань ролі, потрібною самостійністю й наслідками помилки, а не лише за знанням інструмента. Тому в таблиці 2 я не ставив розробнику базового рівня: він сам відповідає за результат.

**13. Які ризики дає недостатній рівень компетентностей?** Витік секретів і персональних даних, вразливі залежності, дефекти й регресії, збої CI/CD перед випуском, повторна робота через нечіткі вимоги. Наслідком можуть бути фінансові й юридичні втрати та втрата довіри клієнтів.

**14. Як цифрові інструменти допомагають реалізувати компетентності?** Вони перетворюють навичку на перевірюваний результат: Git і GitHub дають спільну роботу й історію змін, JUnit дає автотести, GitHub Actions автоматизує збирання, gitleaks знаходить секрети в коді.

**15. Які компетентності найважливіші для обраної ролі?** Для Software Engineer це програмування, співпраця, захист даних, критичне оцінювання й розв’язання технічних проблем: у таблиці 2 вони мають високий рівень. Код є головним результатом праці, review є основним контролем якості, витік даних має юридичні наслідки, помилка у виборі бібліотеки ризикує продуктом, а діагностика збоїв потребує самостійності.

Аналіз показав, що для безпечної розробки замало знати мову програмування: потрібні ще безпека, співпраця, критичне оцінювання джерел і вміння розв’язувати проблеми.
